| 手型纠正做到什么程度？ | 粗粒度姿势纠错（指尖立度、折腕、拇指位置）已被开源工程验证可行 ✅；"精确判断按在第几品"单目摄像头做不到，**不承诺**——用音频（弹出来的音）做正确性真相源，视觉只管姿势（§5.4） |

## 1. 产品定位与用户画像

**目标用户**：非专业、纯爱好、自学电吉他的成年人（首要用户：项目所有者本人，随做随用；其次：同类自学者）。

**三条核心使用场景**：

1. **"这张谱怎么弹？"** —— 拍一张六线谱（纸质书/屏幕/截图），App 识别成可交互谱面，逐段讲解：哪根弦哪个品、左手怎么按、右手怎么拨、用什么技巧，配练习建议。
2. **"我弹得对吗？"** —— 练习时手机支架架好对着手：实时显示手部骨架与即时姿势警报（折腕、手指塌）；每隔一段时间 AI 看关键帧给出像老师回放一样的点评；弹奏同时被麦克风监听，音准/技巧给出反馈。
3. **"降key是什么意思？"** —— 乐理术语随问随答，每个概念都落到大白话 + 吉他上的具体操作（哪一品、怎么按、听起来什么样），不做学院派灌输。

**设计红线**（贯穿所有功能）：
- 术语第一次出现必须有人话解释；
- 给可执行的动作（"指尖垂直按在品丝后面"），不给空评价（"手指再立一点"）；
- 不确定的事直说，不编造（提示词与产品双重约束）。

## 2. 用户痛点（调研结论）

调研方法：中文问答社区（搜狗/头条问答/知乎）、教学站、应用商店多语言区评论、行业文章；由调研 agent 完成检索与溯源（附录 A-2）。

### 2.1 痛点 → 功能映射表

| # | 痛点维度 | 典型表现 / 用户原话 | 对应功能 |
|---|---|---|---|
| 1 | **识谱/乐理门槛** | "吉他谱怎么看？我是个新手什么都不懂""G AM 这些是什么啊？？"；变调夹"夹几品怎么推的，跪谢" | 拍谱讲解 + 谱面点读；移调/变调夹计算器；乐理问答（术语即问即解） |
| 2 | **手型/姿势无人纠正** | "自学者左手按弦和右手手型往往会出错，周围没有人给你指出问题……后来找老师发现姿势都是错的，改起来花了不少时间" | **视觉教练**：实时姿势警报 + AI 关键帧点评（核心差异化） |
| 3 | **练习无反馈、不知道对错** | "学了一年感觉进步好慢""找了老师才知道自己以前全都在瞎练" | 调音/音准判定；riff 跟练对错；AI 周复盘给"下一步练什么" |
| 4 | **电吉他特有：技巧与音色** | 推弦揉弦闷音护弦难学；"效果器参数（Gain/Delay/Reverb）看不懂，只能到处抄参数" | 技巧检测（M4 音频 DSP）；音色向导：说"想要 Metallica 那种音"→ 推荐参数并逐条解释（纯文本任务，深思链胜任） |
| 5 | **资源碎片化、不知练什么** | "网上教程零散杂乱，想到什么练什么"；"教材歌谱一堆，拿起吉他却不知所措" | AI 练习规划：按当前水平 + 目标生成每周计划（DeepSeek 擅长） |
| 6 | **坚持难** | Fender 官方研究：**95% 新手第一年放弃**，多数撑不过 3 个月；"手指疼、枯燥、没成就感" | 成就感设计：第一周就能弹出完整 riff（Smoke on the Water 类）；打卡与进度可视化；AI 鼓励（提示词已内置） |

### 2.2 调研中的两个重要提醒

- **"改手型是最贵的"**：老师访谈一致反映，错误手型一旦定型，纠正成本远高于一开始就学对。所以视觉纠错（痛点 2）应尽早可用，优先级高于曲库类功能。
- **留存即机会**：行业数据（95% 弃学、纯自学练好基本功者不足 30%）说明"反馈缺失"是弃学主因——本项目的每一条反馈链路（调音器 → 音准 → 手型 → 复盘）都在直接命中它。

### 4.0.1 两个重要查证结论

- **ASCII 文本六线谱没有维护良好的开源解析器**（GitHub 检索到的全部无许可证或玩具级）——自研 `TextTabParser` 是正确路线，已按此落地。
- **JVM 生态没有可用的第三方 GP 解析库**（仅 45★ 无许可证项目）——Guitar Pro 导入基本锁定 alphaTab（唯一同时提供渲染+导入+合成的一站式方案）。

### 4.1 关键决策

- **谱面渲染/播放（M2）**：锁定 alphaTab 1.8.4（MPL-2.0，Maven Central，原生导入 GP3-8/alphaTex/MusicXML + 内置 SoundFont 合成）。唯一适配成本：它是 View 控件，Compose 里用 `AndroidView` 包装；MPL 合规要求把改动过的 alphaTab 文件保持开源。自绘 Canvas 仅作为 alphaTab 集成失败时的退路，TabDocument 模型对两者通用。
- **手型姿势判定**：复用 guitar-posture-assistant 的**判定逻辑**（角度阈值），在 Android 用 MediaPipe 重写（原项目是 Python 桌面端）。
- **音频正确性判定（M4）**：单音音准用自家 MPM 已够；和弦/错音比对参考 basic-pitch（转写）与 chroma 模板方案。
- **语音（M3-M5）**：TTS 先用 Android 系统引擎（中文可用、零成本）；ASR 用 sherpa-onnx 端侧模型（Apache-2.0）；两者都有成熟升级路径（云 TTS/ASR）。

## 5. 核心可行性论证：实时"一对一视频教练"

这是本项目最关键的技术判断，值得完整推演。

### 5.1 你想象的样子 vs 技术现实

**想象**：像视频通话一样，老师（AI）实时看着你的手，随时开口："左手抬高一点""这品按错了"。

**现实约束**：
- 全双工实时视频对话需要 Realtime 类 API（视频流持续上行 + 模型流式理解）。GLM-Realtime 类接口存在过但 2026-09 的可用性/价格/质量待验证；DeepSeek 没有视频实时接口。
- 每秒 30 帧全部上传云端：流量与 token 成本爆炸（约 60 倍于预算方案），且当前模型对"连续视频中的细微手型变化"并不比"精选关键帧"更准。
- **但是**：模型不需要每帧都看。手型错误的纠正不需要 30fps 的语言反馈——需要的是"实时的高亮提示 + 定时的语言点评"。

### 5.2 采用方案：三层反馈环

```
┌─ 第0层 · 端侧实时（0ms，0成本，30fps）───────────────┐
│ MediaPipe 手部21点 → 骨架叠加显示 + 规则判定：         │
│   折腕(肘-腕-食指夹角<165°)、手指塌陷(指尖-关节夹角)、  │
│   手是否在画面里、镜头角度引导                         │
│ → 屏幕上即时高亮，不用等网络                           │
├─ 第1层 · 近实时点评（1~3s，低成本，约0.5~2分钟一次）──┤
│ 关键帧抽样（手在画面内+动作变化时才采）→ 1~3帧打包      │
│ → 视觉模型看图点评（结构化JSON：问题/原因/改法）        │
│ → TTS 语音播报 + 屏幕卡片                              │
├─ 第2层 · 随问随答（按需）────────────────────────────┤
│ 用户语音/文字提问："我这样按对吗？""这段怎么弹？"        │
│ → 文本/图片 → 流式回复（DeepSeek/GLM 按任务路由）       │
└──────────────────────────────────────────────┘
```

第 0 层保证"实时感"（有东西一直在看你的手），第 1 层保证"老师感"（自然语言、有教学逻辑的点评），第 2 层保证"一对一感"（随时打断、随问随答）。三者合起来的体验**接近**视频通话教练，而成本只有其 1/50。

### 5.4 精度边界与兜底策略（预期管理）

**诚实结论：单目手机摄像头做不到可靠判品。** 误差来源：
1. **透视**——指板平面与光轴不垂直时，图像中的品距随深度变化，指尖深度（MediaPipe 的 z）只是相对尺度；
2. **遮挡**——按弦时手指互相遮挡、高把位被琴身遮挡；
3. **分辨率**——手机拉远后高把位品丝间距只剩几个像素；
4. **动态标定**——换把/扫弦时手与琴相对运动，静态标定每帧失效。

**对策（三层兜底）**：
1. **音频是正确性的真相源**：你弹出来的音（MPM 测频 → 音名）比"看起来按在哪"可靠得多。视觉说"你按着 C"，音频说"听到的是 E"，以音频为准并提示检查。这条"视听互验"在检索范围内没有严格先例，有 WASPAA 物理模型支撑声学可行性，是本项目的差异化技术点。
2. **视觉只做有把握的事**：姿势类判定（角度阈值）输出即时警报；"参考品位"只在置信度高时显示，UI 标注"参考"。
3. **约束场景而非对抗物理**：引导用户用手机支架固定机位（琴颈斜前方 45°）、练习内容限定低把位起步（开放和弦/前 5 品爬格子）、可选 ArUco 琴头贴纸做一次性标定。把"物理做不到的"转化为"产品引导用户做到的"。

### 5.5 成本与延迟估算（第 1 层点评链路）

按 2026-09 实测口径（DeepSeek 官方：闲时输入 1 元/M tokens、输出 4 元/M、缓存命中 0.02 元/M；高峰工作日白天 ×2。视觉版单张图最多 384 tokens）：

| 场景 | 频率 | 单次 token | 小时成本 |
|---|---|---|---|
| 手型点评（1~3 帧打包） | 练习中每 2 分钟一次 = 30 次/时 | 入 ~2.5K（图 ~1K/帧+提示词）、出 ~0.3K | **≈ 0.07 元/小时** |
| 拍谱识谱 + 讲解 | 每次 | 入 ~1.5K、出 ~1.5K | ≈ 0.005 元/次 |
| 乐理问答 | 随意问 | 入 ~1K、出 ~0.5K | ≈ 0.002 元/次 |

**重度使用（每天 1 小时练习 + 频繁问答）≈ 每月 3~5 元**。控制手段已内建：图片压缩（1024px/质量72）、快答链用 `deepseek-chat`（思考关，token 减半）、只在规划/复盘用 `deepseek-flash`（思考开）、DeepSeek 缓存命中 0.02 元/M（system prompt 固定复用，命中率高）。

### 6.1 可用性实测结论

| 逻辑客户端 | 账号 | Base URL | 模型 id | 实测状态 |
|---|---|---|---|---|
| DeepSeek快答 | DeepSeek 官方 | `https://api.deepseek.com` | `deepseek-chat` | ✅ 全通；思考关（快且省） |
| DeepSeek深思 | DeepSeek 官方 | 同上 | `deepseek-flash` | ✅ 全通；思考开（用户给的 id 正确） |
| DeepSeek视觉 | DeepSeek 官方 | 同上 | `deepseek-v4-flash-vision-exp` | ✅ 全通；实测识别图片成功 |
| 方舟GLM | 火山方舟 | `https://ark.cn-beijing.volces.com/api/v3` | `glm-5-3-flash-260828` | ⚠️ key 有效但账号未开通模型（`ModelNotOpen`），开通后文本可用；元数据标注仅文本输入 |

关键实测发现（详细过程见 docs/模型API接入手册.md）：
- **DeepSeek 的思考开关靠选 id 不靠参数**：`deepseek-flash`/`deepseek-chat` 是同一模型的两种形态；`enable_thinking` 参数被静默忽略；`reasoning_effort` 会给 deepseek-chat 强制开思考——所以代码不传思考参数。
- **方舟模型 id 不用点号**：`glm-5.3-flash` 是 404，正确 id 带日期后缀 `glm-5-3-flash-260828`；且调用前必须在方舟控制台「开通管理」开通，`ModelNotOpen` 错误伪装成 404。
- **方舟版 GLM 元数据 input_modalities=["text"]**：仅文本。若开通后实测支持图片，再补入视觉备份链。
- 若未来需要 GLM 的原生视觉能力，可另申请智谱 BigModel（open.bigmodel.cn）key——网关零改动，设置页填新 baseUrl 即可。

### 6.2 接入要点（已落实到代码）

- 流式结构两家一致：SSE `data: {...}`，正文在 `choices[0].delta.content`（DeepSeek 思考流的 `reasoning_content` 网关自动忽略），`[DONE]` 结束 ✅
- 图片输入：`content[]` 内 `{"type":"image_url","image_url":{"url":"data:image/jpeg;base64,..."}}`（必须 base64 内联）✅
- JSON 输出：`response_format: json_object` + 400 自动降级重试 ✅
- **四个逻辑客户端共享两个账号**（方舟 / DeepSeek），全部 baseUrl 与模型 id 可在 App 设置页修改——换聚合平台/模型更名零代码改动 ✅

### 6.3 路由策略（链式降级）

| 任务 | 链路（按优先级） | 理由 |
|---|---|---|
| 乐理问答（快答） | `deepseek-chat` → 方舟GLM → `deepseek-flash` | 便宜优先、速度优先 |
| 练习规划 / 周复盘（深度） | `deepseek-flash` → 方舟GLM | 思考提升质量 |
| 拍谱识谱 → JSON | `deepseek-v4-flash-vision-exp` → `deepseek-flash` | 视觉实测可用 |
| 谱面讲解 / 手型点评 | 同视觉链 | 需要结合图片 |
| 兜底原则 | 主选失败（限流/网络/未配置）自动换链下一家 | 只配一个账号也能全功能跑 |

## 8. 关键模块技术方案

### 8.1 识谱引擎（三通道）

| 通道 | 输入 | 技术 | 准确性 | 阶段 |
|---|---|---|---|---|
| Guitar Pro 导入 | .gp3~.gp8 文件 | alphaTab 1.8.4（Maven，JVM 生态唯一可用 GP 库） | 高（官方格式） | M2 |
| 文本谱解析 | UG 风格 ASCII tab | TextTabParser（已实现 v0） | 中（启发式） | M1 |
| 拍照识谱 | 谱面照片 | DeepSeek 视觉版 → 严格 JSON → 校验（实测识别可用） | 中（可重拍重试，识别结果可编辑修正） | M2 |

设计要点：**识别与讲解分离**。识谱只产出结构化 `TabDocument`（可校验、可回放、可编辑），讲解基于结构化数据做教学化输出——避免"每次问都重新看图、每次讲得不一样"。

### 8.2 视觉教练（M3）

- 帧源：CameraX ImageAnalysis（后置摄像头，琴颈斜前方 45° 引导页）
- 端侧：MediaPipe HandLandmarker（LIVE_STREAM 模式，GPU delegate）→ 21 点 → Canvas 叠加骨架
- 规则判定（0ms 层）：折腕角（肘-腕-食指 MCP < 165° 警报）、指尖-关节角（塌陷判定）、拇指位置分区、双手在框检测 + 镜头引导
- 关键帧层：手在框内 + 每 90~120s（或姿势突变）采 1~3 帧 → 视觉模型点评 → TTS
- 提示词已内置"看不清就说，不硬猜"约束，防误报

### 8.3 音频引擎（M0-M4）

- M0（已实现）：MPM 音高检测（4096 点 @44.1kHz，首个峰规则抗八度错误 + 抛物线插值）→ 调音器
- M4：riff 跟练（目标音序列 vs 实测音序列的时序对齐判定）；推弦/揉弦（音高曲线连续追踪）；闷音/杂音（频谱特征）
- M5：和弦识别（chroma 模板）+ 跟谱 DTW 对齐

### 8.4 乐理教练

- 交互：流式聊天 + 常用概念卡片（调/移调/变调夹/五度圈/强力和弦/闷音护弦）+ 指板可视化（点一个音看全指板位置）
- "降key/升key"类问题的答案结构已在提示词中固定：原调 → 新调 → 具体操作（换指法/变调夹夹几品）→ 听感变化 → 立即试的小练习
- 痛点调研中的 8 个高频问题（六线谱怎么看/变调夹夹几品/大小调区别/五声音阶先练哪个/琶音是什么/为什么有杂音/效果器参数/和弦构成）直接构成 M1 的概念卡片清单

### 8.5 语音

- TTS：M3 用 Android 系统 TTS（中文、零成本）播报点评；M5 可评估云 TTS（如 GLM-TTS，许可未核实，暂不引入）
- ASR：M5 用 sherpa-onnx v1.13.8（Apache-2.0；无 Maven 坐标，从 GitHub Release 下载 AAR 放 `app/libs`）+ 中文流式模型 `sherpa-onnx-streaming-zipformer-zh-14M-2023-02-23`（仅 14M，端侧实时）

### 8.6 数据与记录（M1 起）

- Room 表：练习记录（日期/时长/内容/调音与手型问题留档）、曲目库（TabDocument 持久化 + 进度标记）
- AI 周复盘：DeepSeek 读一周记录 → "本周练了什么、哪里进步、下周建议"（痛点 5 的解法）

### 8.7 图片谱逐句大白话讲解（2026-09-15 调研定稿，用户需求）

**路线结论：走"结构化优先"（路线 B）**——识谱→TabDocument→逐句生成讲解，不做"模型直接看图即席讲解"。理由：准确性可程序化审计（防漏音/错音，通用视觉模型对密集六线谱的误读是已知痛点）；成本可控（图只编码一次）；交互性强（点哪讲哪、跟播高亮都建立在结构化索引上）。讲解 UI 仍展示原图作对照，位置引用用"第 X 小节第 Y 拍"这类谱面索引。

**切分粒度（三层）**：段落级概览（一段话建立地图）→ **乐句级讲解（默认单元，2-4 小节/句）** → 音符级点读（兜底，点任何音只讲该音）。固定讲解结构：一句话总述 → 左手怎么按（含指法编号）→ 右手怎么弹 → 术语大白话 → 难点提示 → 自查问题。

**防漏音关键设计（CoVe 覆盖审计）**：讲解生成后，剥离讲解文本、仅凭 TabDocument 让模型重列音符清单，与讲解覆盖集合比对，不一致则重写——把"不漏音"从软约束变成可程序化校验。

**自动指法**：自研动态规划（换弦/跨把位/伸展代价，参考 MIT 6.006 Guitar Fingering 与 arXiv:2407.09052 的约束思路）产出手指编号(0-4)与把位建议；LLM 生成的指法必须过规则校验。不存在拿来即用的开源指法库（已调研确认）。

**交互分期**：Phase 1 乐句卡片式点读 + 整段 TTS 朗读（M2）→ Phase 2 逐音高亮跟播 → Phase 3 先讲后练闭环（对应 F207-F209）。

### 8.8 扒谱：音频/视频 → 六线谱（2026-09-15 调研定稿，用户需求）

**MVP（端侧，0 成本）**：视频/音频 → Media3 抽 PCM（FFmpeg-kit 已退役，不引入）→ **basic-pitch ONNX**（Spotify，Apache-2.0，约 20-30MB）跑 onnxruntime-android → 音符事件 → **自研 DP 弦/品分配**（与 F209 共用内核）→ 节拍量化（onset+测速起步）→ TabDocument 入曲库。主打**干净录音的单音 riff / 分解和弦**——质量预期如实：清音单音良好、分解和弦可用会漏音、**失真强力和弦与带鼓混音是技术天花板，不承诺**。

**云端增强（可选付费）**：Demucs 音源分离 → 云端转写 → madmom 量化，预估单次 0.1-0.5 元，作"高清模式"。

**风险**：失真音色谐波导致八度偏移/漏音；复音与弦间共鸣；分离伪影双误差累积；版权灰色地带（需免责声明）。直接"音频→六线谱"的研究模型（TART/SynthTab/GAPS）目前只对独奏吉他成立，作长期跟进。对应特性 F601-F604（M6）。

| 3 | 模型 API 变更（id/参数/价格） | baseUrl 与模型 id 全部可配置；网关层隔离；关键参数（thinking 等）显式传不依赖默认值 |
| 4 | 成本失控 | 已内建：图片压缩、帧率预算、reasoning_effort=low、DeepSeek 峰谷错峰；预算告警（月度 token 统计） |
| 5 | 许可证合规 | 只引入 Apache/MIT 代码；GPL/AGPL（TuxGuitar、Audiveris、TarsosDSP）仅参考格式文档/算法思路 |
| 6 | 密钥安全 | 仅存本机 DataStore；若未来公开发布，加自建轻量代理，密钥不出服务端 |
| 7 | 手机性能（视觉+音频并行） | MediaPipe GPU delegate；MPM 如功耗过高换 FFT 实现；两引擎分时复用 |
| 8 | 范围蔓延（个人项目最大风险） | 每个里程碑以"自己真的会用"为准验收；曲库/社区/音效类功能一律后置 |
